# DiploChain User Guide

## 1. What the software does

DiploChain issues, anchors, revokes, and verifies academic credentials in the W3C Verifiable Credential (VC 2.0) format backed by an Ethereum-compatible (EVM) blockchain. Holder personal data stays exclusively inside the credential `.json` file. The blockchain stores accredited issuers, each issuer's key history, batch Merkle roots, and revocations.

In the local environment, the governance, issuer, relayer, and recovery accounts are preconfigured automatically. The relayer submits signed transactions and pays gas, while verifiers run public read-only queries without an account or login.

## 2. Files used by the system

Before operating the tabs, review the two file types accepted by the interface.

- **Credential `.json` file** is the digital credential generated by DiploChain itself. You obtain it on the **Issue** tab by clicking **JSON** on an issued credential (for example, `vc-maria-silva.json`). It stores the holder data (name, course, workload, and dates), the `salt`, the issuer signature, and the blockchain anchor reference. The holder keeps this file and delivers it to a verifier for checking on the **Verify** tab or in the CLI.
- **Batch `.csv` file (optional)** is a plain-text list of holders used only on the **Issue** tab (**Batch** mode), similar to a spreadsheet exported from Excel or an academic system. Each line represents one holder and accepts two formats separated by commas or semicolons. The single-column format lists one holder name per line and reuses the default course and workload from the form. The three-column format specifies `name,course,workload_hours` on each line. If the first line starts with `name` or `holder`, it is treated as a header and skipped automatically.

## 3. Access and network settings

After starting the local environment as described in [README.md](./README.md), open `http://localhost:5173`. The locally deployed contract address loads automatically.

To inspect or change the network, click **Network** (or **Configure network**) in the top-right corner. The drawer lets you edit the **RPC URL**, enter a different contract address (such as a Base Sepolia testnet deployment), click **Reconnect**, and inspect the addresses of the four configured accounts (governance, active issuer, relayer, and recovery).

## 4. Issue credentials (Issue tab)

The **Issue** tab operates with the default issuer `did:web:extensao.ufsc.br` and provides **Single** and **Batch** modes.

- In **Single** mode, enter the holder name, course, workload, and optionally an **Expiration date (optional)**. Clicking **Issue and anchor credential** signs the credential, computes a single-leaf Merkle tree, and anchors the root in the contract through the relayer.
- In **Batch** mode, type the list of holders (one name per line) or click **Import .csv** to load a `.csv` file matching Section 2. Clicking **Anchor batch** places all credentials into the same Merkle tree and anchors them in one transaction, displaying total gas and gas per credential.

Generated credentials appear in the **Issued credentials** list on the right (for large batches, the first 20 remain listed). Each entry provides four actions.

- **Verify** sends the credential directly to the **Verify** tab and runs validation.
- **QR Code** opens the visual credential card with a scannable QR Code and an **Open direct verification** link.
- **JSON** downloads the credential `.json` file for delivery to the holder or later verification.
- **Revoke** records a permanent revocation in the contract with the code selected under **Revocation reason** (`AdminError`, `IssuerError`, `Fraud`, or `Superseded`).

At the bottom of the issuance form, **Rotate key** replaces the active key `#key-2026-1` with `#key-2027-1` in the contract. Credentials anchored before rotation remain valid, and subsequent issuances use the new key.

## 5. Verify credentials (Verify tab)

The **Verify** tab serves any verifier who receives a credential produced on the **Issue** tab.

1. Drag the credential `.json` file into the **Credential (.json)** dropzone or click it to pick the file from your computer.
2. To paste the `.json` contents instead, click **Paste JSON manually**, insert the text, and click **Verify JSON**.
3. Opening a link generated by the **QR Code** button (`/?vc=...`) loads and verifies the credential automatically.

The right panel displays the verdict (`VALID`, `VALID - ISSUER CLOSED`, `REVOKED`, `ISSUER SUSPENDED`, `ISSUED AFTER KEY COMPROMISE - UNDER REVIEW`, `INVALID SIGNATURE`, `TAMPERED`, `ISSUER NOT REGISTERED`, `ANCHOR NOT FOUND`, or `EXPIRED`), query latency, computed `leafHash`, and four separate cards.

- **1. Authenticity** indicates whether the ECDSA secp256k1 signature, salted hash (JCS), and Merkle proof match the anchor recorded in the contract, displaying the transaction hash (`tx`).
- **2. Issuer** shows the issuer DID, assurance level (`L1` or `L2`), and current registry status (`Active`, `Suspended`, or `Closed`).
- **3. Academic Validity** presents the issuer's own assertion inside the credential, stating that academic and legal recognition remain outside technical verification.
- **4. Revocation & Expiry** confirms whether the `leafHash` appears in the issuer's revocation registry (with its reason code) and whether `validUntil` has passed.

## 6. Manage issuers and keys (Governance tab)

The **Governance** tab gathers operations performed by the governance account and the recovery account.

In **Registered issuers**, each issuer displays its DID, assurance level, status, and registered key table. Status buttons let you **Suspend** an active issuer (making its credentials return `ISSUER SUSPENDED`), **Reactivate** a suspended issuer, or permanently **Close** the issuer (`Closed`, keeping prior credentials valid as `VALID - ISSUER CLOSED`).

To report a compromised key, set **Compromise date/time** at the top of the panel and click **Report compromise** on the affected key row. The recovery account signs `reportCompromise` via EIP-712 and blocks further actions by that key. Credentials anchored before the reported timestamp stay `VALID`, while credentials anchored at or after that timestamp return `ISSUED AFTER KEY COMPROMISE - UNDER REVIEW`.

In **Register issuer** on the right, enter the new issuer DID, select an assurance level (`L1` or `L2`), and click **Register issuer**.

## 7. Terminal verification (CLI)

Any `.json` file downloaded from the **Issue** tab can be verified independently from the terminal by querying only the blockchain.

```bash
cd core && npm run verify -- <path-to-file.json>
```

The command prints the verdict, verification time, `leafHash`, and the result for all four dimensions. When using another network or contract, pass the optional flags `--rpc <url>` and `--contract <address>`.
